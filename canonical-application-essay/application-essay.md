### Engineering Experience
At Eden, we primarily worked in the AWS environment, and utilized a variety of languages such as TypeScript, Python, and Lua. We used DynamoDB for a no-SQL database, with our primary backend services executed via Lambda functions and EC2 instances. Our CI/CD and infrastructure was managed through AWS CDK for IaC, and a private NPM registry handled our software packages.

At Wishroute, we also primary utilized AWS, with orchestration of our key Lambda functions achieved through State Machines and Step Functions. During my internship there, my project focused on developing analytics dashboards from internal data, meaning I interacted regularly with both our no-SQL DynamoDB tables and our migrated analytics data in Postgres. 
        
I would describe myself as a high quality coder, a description which stems from a position I hold that any code that compiles will be understood by the machine, but socially-conscious code is what will be understood by future developers. Keeping both of these audiences in mind while designing software is key, as ensuring that code will be understood by future developers is key to sustainable software development.

While at Eden, I designed and implemented a major expansion to our backend services, opting for a microservice architecture, in large part  because of the business position of the organization, where the needs of our three key stakeholders meant that such an architecture created a structure which can serve the different parties successfully while maintaining efficiency and maintainability. Furthermore, encapsulating strict functionality into microservices allowed us to decouple our development, which was key for our staff makeup, with a small team of interns and an off-shore team supplementing our short-term product needs. This backend architecture needed to support two-way communication between insurance providers, healthcare providers, and patients. Each of these three external parties needed access to non-distinct subsets of our features, so designing these features using loosely coupled services allowed for flexibility as these feature subsets evolved, interactions with external partners changed, new features were developed, and as team make-up evolved. Finally, this design allowed for decoupled parallel development across timezones and evolving timelines, which was especially critical to maximize development in partnership with our offshore team.

Quality of software, and hence software development relies on symbiosis between user and system for achievement of some defined outcome. By balancing system's engineering needs with the needs, habits, and sensitivities of users, high quality software can be achieved. These engineering and user needs change based on the environment, goals, existing software paradigms, in that how software is designed or developed and how a user expects to interact with software fluctuate with different user-bases and are critical for alignment between user and software. From the perspective of the software engineer, centralizing end user experience with respect to key internal systems and architecture will allow high quality software to emerge.

Effective documentation in large software projects is a balance of abundance of information with concision. Documentation should have a clearly defined audience. This can be a specific team, or someone with a specific use for reading the documentation. For example, documentation for a developer who interacts with a software component externally (e.g. using a function from a library) needs to focus on how the component responds to external inputs, and their influence on its behavior. In other words, this documentation purpose necessitates the creation of a clear contract or expectation of behavior for the component. Alternatively, a developer that is tasked with refactoring the component has a different need that documentation can fulfill. In this context, the focus of the documentation should be on how the internal systems were designed, including the considerations, restrictions, pressures, business needs and overall circumstances of the design at the time. At times, these audiences are at odds with one another when it comes to effective documentation. In short, I believe effective documentation should deeply consider its intended audience, and should not be written to merely check a box.

In my opinion, UX should flow. Said flow is based on the users needs, their familiarity with the software and use case, the users background, and their preconceptions of the software. As much as possible, development teams should minimize the gap between developers and users to maximize the ability for the UX to match the higher level needs of the software-user partnership. For example, software that is used by trained professionals for many hours a day should prioritize features like key-bind customization or macro support, while software that expects low familiarity should focus on highly visual interaction, where every interaction option a user has is displayed to them.

As with other aspects of software engineering, performance should also be a balance between efficiency, maintainability, utilization of current technology. In risk of repeating myself, it matters greatly how the software is being used. If an action is only taken 100 times a day, investing in a performance upgrade of 0.1s will yield less benefit than the same upgrade on an action that is taken 100k times per day. How valuable is the development investment versus the tangible outcome of a performance improvement. Additionally, performance can come at the cost of increased maintenance overhead, and advances in technology can yield performance upgrades passively. 

Security should be an ensemble approach where faults are expected but not welcomed. It is prudent to always assume a security measure will be breached at some point, and to fully game out the consequences of a breach. Enough security cover should be created to minimize a cascade of breaches. By clearly outlining attack surfaces, determining how a breach in security would affect various software components and critical information or secrets, and how Cyber Security best practices and techniques can apply to a specific situation, engineers can improve their security posture and awareness.

I have limited experience with DevOps and DevSecOps, but from my experience, utilizing IaC to create automatic, repeatable deployments takes extra up front investment, but is worth the effort, especially as infrastructure increases in scale and complexity. Utilizing federated authentication services is also good because of the fact that if a single use key is compromised, a breach does not compromise future deployments. As with other aspects of software engineering, balancing granularity with coupled deployments and ensuring that feature deployments can target specific infrastructure sets will improve the sustainability of continuous development cycles.

### Domain Specific Experience
My beliefs on open source development are that it should be the primary development mode in a perfect world. As more aspects of our daily lives are increasing intertwined with technology and software, the transparency and user focused philosophy naturally pushes towards sustainable, transparent software, aimed at real improvements of the users lives and direct utility. In open source projects, structuring the *meta infrastructure* is extremely improtant in order to leverage the community that open source software can foster. By establishing clear lines of discussion in terms of product direction; SOPs for contributions, bug reporting and fixes; as well as installation and extension documentation; the *development load* can be distributed among a community of contributors. This can lead to a degree of self-sorting, allowing people to find their niche and maximize their contributions. Of course, this opens a whole new dimension of maintenance, but when organized and communicated thoughtfully with just enough structure to maintain order and velocity, an open-source project can operate at a high level of efficiency while delivering a quality user-focused project that is available to all. Unfortunately, I have not directly contributed to any open source projects, but in the future once I feel I have the experience, time, and alignment with a project I care about, I would very much like to make those contributions.

My knowledge of a Linux distribution is at a moderate level, having used Ubuntu exclusively for almost 16 months. In that time I have familiarized myself with the basics of interacting with the system, making personalization, and leveraging its incredible features. It is an almost weekly occurrence that I am learning of new systems, features, or strategies that Ubuntu makes possible that improve my user experience, or open up new possibilities with respect to integrations with other software systems. From my understanding, a Linux distribution consists of the operating system and then a desktop environment. The operating system interacts with the kernel and low-level systems to carry out processes and facilitate user interaction and behavior in said desktop environment. In that sense, different distros have different ways for user interaction with the computer, and offer different levels of guardrails and exposition of internal systems to users. Similarly, the modular nature of distros allows for a whole gradient of user experiences, all built on common low-level software to some extent or another. I have gained my limited knowledge of Linux distributions through various efforts to personalize my computational experience over the last 16 months, as well as troubleshooting various issues that have arisen in my system throughout that time. For example, I was experiencing an issue with my Bluetooth connection, necessitating my investigation of the various daemons and services that govern Bluetooth and manage the service for the user. After tracing the issues all the way to my Bluetooth card, I was able to determine that my motherboard was not giving any power to the card, and hence the service was not working at all.

With respect to software packaging, I have had limited exposure, but at Eden we utilized a private NPM registry for our package management and deployment. Combined with AWS CDK for IaC and GitHub Actions for CI/CD, this is how we managed our software packages. Some of our micro-services utilized Docker for their builds on various AWS services like EC2.

To engineer a release pipeline for a major software project, I would first build a simple automated pipeline that initiates on changes merged into main. This would trigger linting and automated test harnesses, create the build artifact, and then deploy to a staging environment for validation. In terms of automating this process, a CI/CD service such as GitHub Actions or a basic Jenkins setup alongside Docker would provide automated and standardized builds. Within this process, critical steps before a release would need to include extensive code review, automated test validation, and checking release notes and updating deployment documentation before promotion to production can occur.
